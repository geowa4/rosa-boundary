# PART B — CLI and AWS identity chain

## B.1 Scope & boundaries

In scope: the runtime chain from an SRE's OIDC login through the CLI token cache, config resolution, two-step `AssumeRoleWithWebIdentity`, SigV4 Lambda invocation with the `x-oidc-token` header, Lambda-side JWT validation/authorization, the ABAC-tagged resources it creates, the SRE-role operations (`ExecuteCommand`, `StopTask`, EFS cleanup), and every IAM artifact that enforces identity (trust policies, permission policies, resource policies, KMS key policy, Lambda function URL auth). Reaper and task/execution roles are covered at the IAM-assertion level only.

Out of scope: OCM credential injection (separate issuer/client), Trusted Actions, Terraform apply, image build/delivery, audit-sync internals, the in-container shell.

### Trace B8 — mid-workflow token expiry

- CLI-side: each STS call re-reads the cache; a token within 30 s of `exp` is treated as expired → fresh human login (browser/device) in the middle of `start-task` step 4 ([start_task.go#L149-L155](https://github.com/geowa4/rosa-boundary/blob/509078b/internal/cmd/start_task.go#L149-L155); [token.go#L91-L97](https://github.com/geowa4/rosa-boundary/blob/509078b/internal/auth/token.go#L91-L97)). The already-created task/AP persist (no rollback).
- Lambda-side: validation happens once at invocation; a token that expires during the 300 s Lambda run is irrelevant.
- STS credentials (1 h default) outlive the typical ECS Exec setup; whether an established SSM session survives credential expiry is UNVERIFIED (plugin uses creds to open the channel).
- No refresh tokens anywhere; `oidc_session_duration` only bounds STS session length, not the ID token.
