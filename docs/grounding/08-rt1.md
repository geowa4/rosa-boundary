# PART A — Container runtime and interactive session

## A.1 Scope & boundaries

In scope:
- What happens inside the Fargate task from container start (`ENTRYPOINT`) to exit: `entrypoint.sh`, `Containerfile` runtime facts, `skel/sre/`, `utils/rosa-boundary-credential-helper`.
- Task definition runtime shape from `deploy/regional/ecs.tf` and the per-investigation clone registered by the create-investigation Lambda (`lambda/create-investigation/handler.py`), only as far as it changes what runs in the container (env vars, volumes, secrets, tags).
- The optional `kube-proxy` sidecar.
- IAM permissions the running container can exercise (task role grants in `deploy/regional/iam.tf`), vs. the execution role.
- Network path from the task: `deploy/network/vpc.tf`, `deploy/regional/bedrock-endpoint.tf`, `deploy/regional/ecs.tf` security group.
- `join-task` / `start-task --connect` flow: `internal/cmd/join_task.go`, `internal/aws/ecs.go`, `internal/aws/session.go`.
- OCM credential configure/clear: `internal/cmd/credentials*.go`, `internal/credentials/ocm/**`, in-container helper.
- `claude` / Bedrock path at runtime: which resources are read/written when an SRE invokes `claude` inside the container.

Out of scope (covered by other domains): OIDC login and role assumption on the laptop, Lambda create-investigation request validation/ABAC decisions (only its outputs that reach the container are listed), reaper decision logic beyond its effect on the container's signals, Trusted Actions.

Part B (below) covers the audit artifacts produced by these flows.

### Trace A-6: `kube-proxy` sidecar (only when `enable_kube_proxy = true`)

1. Base task def includes container `kube-proxy` (same image), `essential=true`, `readonlyRootFilesystem=true`, `/tmp` from empty volume `proxy-tmp`, `HOME=/tmp`, command `printf '%s' "$KUBECONFIG_DATA" > /tmp/kubeconfig && exec oc proxy --address=127.0.0.1 --port=${port} --kubeconfig=/tmp/kubeconfig`; health check `curl -sf http://127.0.0.1:${port}/version` every 10 s, timeout 5, retries 3, startPeriod 30 (https://github.com/geowa4/rosa-boundary/blob/509078b/deploy/regional/ecs.tf#L175-L224).
2. The **base** definition has no `secrets` entry; `KUBECONFIG_DATA` is injected only by the Lambda clone as a Secrets Manager `valueFrom` partial ARN `arn:aws:secretsmanager:<region>:<acct>:secret:rosa-boundary/clusters/<cluster_id>/kubeconfig`; the execution role can read `secret:${project}/*` (https://github.com/geowa4/rosa-boundary/blob/509078b/lambda/create-investigation/handler.py#L620-L624 ; https://github.com/geowa4/rosa-boundary/blob/509078b/lambda/create-investigation/handler.py#L664-L672 ; https://github.com/geowa4/rosa-boundary/blob/509078b/deploy/regional/iam.tf#L79-L90). A base task launched directly (not via Lambda) with the sidecar would write an empty kubeconfig and fail health.
3. The main container `dependsOn` `kube-proxy: HEALTHY`; the proxy exposes an unauthenticated plain-HTTP cluster API on the task's loopback (awsvpc shares the network namespace across containers), with the cluster credential never visible to the `sre` container (sidecar has no credential or home mounts: https://github.com/geowa4/rosa-boundary/blob/509078b/deploy/regional/ecs.tf#L201-L207 ; tests https://github.com/geowa4/rosa-boundary/blob/509078b/lambda/create-investigation/test_handler.py#L2439-L2528).
4. Staging HCP workspace does not set `enable_kube_proxy` (grep of `hcp-terraform/rosa-boundary/main.tf` finds no key) → default `false`; sidecar is absent in staging at this commit.
